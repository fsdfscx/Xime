# LeanType 输入法「视觉行」编辑能力实现分析

> 分析对象：`github.com/LeanBitLab/LeanType`（HeliBoard 的 fork，Kotlin，GPL-3.0）
> 抓取时间：2026-11，`main` 分支；`compileSdk 36 / minSdk 21 / targetSdk 35`
> 本文所有 `文件:行号` 均对应该分支快照。

---

## 0. 结论先说

你在「换视觉行」上遇到的问题，本质上是 **IME 拿不到编辑器的 `Layout`**。LeanType 没有硬算，而是分三层降级：

| 层级 | 手段 | 精度 | 适用 |
|---|---|---|---|
| A | 把移动**委托给编辑器**（`sendKeyEvent` 发 `DPAD_UP/DOWN` + `META_SHIFT_ON`） | 最准（编辑器自己用 `Layout.getLineForOffset`） | 方向键、空格上下滑、触摸板 |
| B | `InputConnection.requestTextBoundsInfo()`（Android 14+）+ `CursorAnchorInfo`，**自己重建视觉行** | 准（逐字符矩形） | 需要固定锚点任意扩选（删除键二维滑选） |
| C | 纯文本启发式：`\n` 分段 + 每 ~40 字符在空白处断行 | 粗（软换行会错） | B 不可用/超时的兜底 |

**关键判断：如果你的「换视觉行」只是"上/下移一行光标"，不要去算。直接发 DPAD 键事件，让编辑器自己处理软换行。** 只有当你要"锚点固定、任意跨行扩选/收缩"时（B 路径），才需要自己重建几何 —— 这正是 LeanType 唯一自己算行的地方，也是坑最多的地方。

## 2. A 路径：把移动委托给编辑器

### 2.1 普通移动

方向键最终落到 `InputLogic.kt:1005-1027`：

```kotlin
val keyEventCode = KeyCode.keyCodeToKeyEventCode(keyCode)   // ARROW_UP -> KEYCODE_DPAD_UP
...
sendDownUpKeyEventWithMetaState(keyEventCode, event.metaState)
```

`KeyCode.kt:266-274` 的映射：

```kotlin
ARROW_UP          -> KeyEvent.KEYCODE_DPAD_UP
MOVE_START_OF_LINE-> KeyEvent.KEYCODE_MOVE_HOME
MOVE_END_OF_LINE  -> KeyEvent.KEYCODE_MOVE_END
PAGE_UP           -> KeyEvent.KEYCODE_PAGE_UP
```

这些键事件由系统 `TextView`/`Editor` 消费，**软换行的行距、行首列对齐、RTL 全部由编辑器算**，IME 侧零成本、零误差。

**注意一个细节**：`MOVE_START_OF_LINE` 映射的是 `KEYCODE_MOVE_HOME` 而不是"自己找 `\n`"。因为 `EditText` 对 `MOVE_HOME` 的实现就是"视觉行行首"，而不是逻辑行首 —— 这正是你要的语义。别用 `getTextBeforeCursor().lastIndexOf('\n')` 去模拟，那样拿到的是**逻辑行**。

### 2.2 选择模式

`KeyboardActionListenerImpl.kt:188-235`：

```kotlin
val isSelecting = keyboardSwitcher.keyboard?.mId?.isAlphabetShiftedManually == true
                  || sPersistentSelectionModeActive
if (isSelecting) {
    val eventTime = SystemClock.uptimeMillis()
    connection.sendKeyEvent(KeyEvent(eventTime, eventTime, ACTION_DOWN, KEYCODE_SHIFT_LEFT, 0, 0))
    connection.sendKeyEvent(KeyEvent(eventTime, eventTime, ACTION_DOWN, androidKeyCode, 0, META_SHIFT_ON))
    connection.sendKeyEvent(KeyEvent(eventTime, eventTime, ACTION_UP,   androidKeyCode, 0, META_SHIFT_ON))
    connection.sendKeyEvent(KeyEvent(eventTime, eventTime, ACTION_UP,   KEYCODE_SHIFT_LEFT, 0, 0))
}
```

**这是最容易踩的坑**：只给 `KeyEvent` 携带 `META_SHIFT_ON` 是不够的。WebView / 部分 contenteditable 只根据"是否有 SHIFT 按下事件"来决定扩选，不读 metaState。必须**真的补一对 `SHIFT_LEFT` down/up**。

退出选择模式时（`:211-224`），他们把光标收拢到选区末端而不是起点，避免用户以为"取消选择后光标应该跟手"。

## 3. B 路径：请求编辑器几何，自己重建视觉行

这是删除键二维滑选用的方案，也是全文最值得抄的部分。

### 3.1 前置：拿到光标锚点

`InputLogic.startInput()` :158：

```kotlin
mConnection.requestCursorUpdates(true, true)   // CURSOR_UPDATE_MONITOR | CURSOR_UPDATE_IMMEDIATE
```

`LatinIME.onUpdateCursorAnchorInfo()` :1088 存进 `RichInputConnection.lastCursorAnchorInfo`（:1571）。

只有拿到 `CursorAnchorInfo` 才能知道"光标这一行的 top/bottom"，进而算出 `lineHeight`，用来构造查询矩形。**如果你的输入法根本没请求 cursor updates，B 路径第一步就走不通。**

### 3.2 查询矩形

`requestExactLines()` :670-689：

```kotlin
if (Build.VERSION.SDK_INT < UPSIDE_DOWN_CAKE) return        // Android 14+
if (!keyboardId.isMultiLine) return                          // 只对多行编辑框
if (editorPackage == noTextBoundsPackage) return              // 该 App 已知不支持，本次运行不再问

val anchor = connection.lastCursorAnchorInfo ?: return
val lineHeight = anchor.insertionMarkerBottom - anchor.insertionMarkerTop
if (lineHeight <= 0f) return

val baseStart = deleteSwipeStartForExactLines()
val bounds = RectF(-HUGE_HORIZONTAL,
                   anchor.insertionMarkerTop - EXACT_LINES_LOOKUP * lineHeight,  // 向上 40 行
                   HUGE_HORIZONTAL,
                   anchor.insertionMarkerBottom)
sendExactLinesRequest(bounds, generation, baseStart, editorPackage)
```

常量（:1290-1294）：`EXACT_LINES_LOOKUP = 40`、`MAX_EXACT_LINES_CHARS = 4000`、`EXACT_LINES_TIMEOUT_MILLIS = 150`、`HUGE_HORIZONTAL = 100_000f`。

`HUGE_HORIZONTAL` 是为了覆盖任意滚动位置、任意宽度 —— 查询矩形是**编辑器坐标系**，不是屏幕坐标。

### 3.3 异步竞态处理（重点）

`sendExactLinesRequest()` :690 + `onExactLinesResult()` :713，一共四道保险：

1. **generation**：每次滑选开始 `deleteSwipeGeneration++`，回调里比对，丢弃过期结果。
2. **pending 步数缓冲**：等待期间纵向步数累加到 `deleteSwipePendingStepsY`，`stepsY` 置 0，回调后 `moveDeletePointer(0, pending)` 补做 —— 用户滑动不会"卡住丢失"。
3. **150 ms 超时**：超时按 `info == null` 处理，回落到 C 路径。
4. **一次性重试**：有些编辑器只返回请求区域的一部分（注释里明确写了"seen: only the first line"）。若 `info.endIndex < baseStart || info.startIndex > baseStart`，用全文本矩形再问一次（:717-725）。
5. **包名黑名单**：彻底失败后记 `noTextBoundsPackage`，本次键盘生命周期内不再浪费 IPC。

**如果你也发了请求但结果"时好时坏"，90% 是缺了 1/2/4 中的某一个。**

### 3.4 从字符矩形重建视觉行

`geometryFromTextBoundsInfo()` :744-777：逐字符 `getCharacterBounds()` 取 `top/bottom/left/right`，再取 `FLAG_CHARACTER_LINEFEED`，交给 `VisualLines.lineStarts()`。

```kotlin
// VisualLines.kt:lineStarts —— 纯函数，无 Android 依赖，可单测
fun lineStarts(start: Int, tops: FloatArray, bottoms: FloatArray, lineFeed: BooleanArray): List<Int> {
    val starts = mutableListOf(start)
    var lineTop = tops[0]; var lineBottom = bottoms[0]
    for (i in 1 until n) {
        val centerY = (tops[i] + bottoms[i]) / 2
        val newLine = lineFeed[i - 1] || centerY > lineBottom || centerY < lineTop
        if (newLine) {
            starts.add(start + i); lineTop = tops[i]; lineBottom = bottoms[i]
        } else {
            lineTop = minOf(lineTop, tops[i]); lineBottom = maxOf(lineBottom, bottoms[i])
        }
    }
    return starts
}
```

三个设计点值得学：

- **用 `centerY` 而不是 `top` 判行**：混排字号（emoji、上标、行内图片）时同一视觉行的 `top` 可能不同，`centerY` 更稳。
- **`lineFeed` 标志优先**：硬换行处即使几何完全一致也要断行（空行、行高为 0 的情况）。
- **行区间用 min/max 累积**，容忍倾斜/测量噪声。

### 3.5 首行不完整问题（很隐蔽）

查询矩形从"光标上方 40 行"开始，**起点通常不在行首**，所以 `starts[0]` 是假行首：

```kotlin
// :771-776
val charBefore = ...  // start 前一个字符
val firstIsRealLineStart = start == 0 || charBefore == '\n'
val realStarts = if (firstIsRealLineStart) starts else starts.drop(1)
```

漏掉这个判断，你的行索引会整体错一行 —— 表现就是"上移一行，选区却少/多选了一行"。

### 3.6 同列对齐

`VisualLines.LineGeometry`：

```kotlin
fun xAt(offset: Int): Float                                  // 光标在 offset 处的 x
fun lineIndexOf(offset: Int): Int                            // 二分查行
fun columnOffset(line: Int, x: Float): Int                   // 该行中 left 最接近 x 的字符 offset
fun boundaries(baseStart: Int, x: Float): List<Int>          // 从 baseStart 逐行向上的锚点表
```

`boundaries()` 返回的是**一组候选偏移**，索引 0 = 当前锚点，1 = 上一行同列…… 这样上下滑动只是改索引，不用每次重算，也天然支持"往下滑撤销多选的行"。

`columnOffset()` 是线性遍历该行所有字符取最近 —— 行内字符数有限（≤ 一行宽度），可以接受；比二分更适合"字符宽度不等"的情况。

## 4. C 路径：启发式兜底

`getLineBoundariesBackwards()` :1298-1345：

```
从光标往前：
  1. 找上一个 '\n'，得到逻辑行 [lineStart, currentEnd)
  2. 若该段 > 50 字符，按每 40 字符往回找最近的空白处断一次
  3. 一直推到文本开头
```

它只能近似"软换行"，而且：

- 中文没有空白，40 字符断点会落在词中间；
- 只按字符数、不看字号/宽度；
- 只能取**光标前 2000 字符**（`getTextBeforeCursor(2000, 0)` :591），长文会截断。

**结论：这条路径只配当兜底。如果你的"换视觉行"最终落到这里，行为一定不稳。**

## 5. 扩展/收缩选区的状态机

删除键二维滑动是「锚点固定在选区末端，向左/上扩展」的模型。状态变量（:552-576）：

| 变量 | 含义 |
|---|---|
| `deleteSwipeInitialEnd` | 锚点（选区 end），整个手势期间不变 |
| `deleteSwipeInitialText` | 锚点前 2000 字符快照，用于词/行边界计算 |
| `deleteSwipeLineBoundaries` | 行锚点表（B 精确 / C 估算） |
| `deleteSwipeLineIndex` | 当前行索引（0 = 起始行） |
| `deleteSwipeCharOffset` | 在行内向左的字符偏移（正 = 已多选） |
| `deleteSwipeWordIndex` | 词模式下的词索引（可负 = 反向取消） |
| `exactDesiredX` | **期望保持的水平位置**（列） |

核心不变量：

```kotlin
finalStart = (lineBase - charOffset).coerceIn(0, deleteSwipeInitialEnd)
connection.setSelection(finalStart, deleteSwipeInitialEnd)   // 顺序永远是 start < end
```

`prepareExactVertical()` :630-650 是灵魂：

```kotlin
if (exactDesiredX.isNaN() || exactHorizontalMoved) {
    exactDesiredX = g.xAt(current)                // 只在"第一次纵向"或"刚横移过"时重取列
    exactHorizontalMoved = false
    deleteSwipeLineBoundaries = g.boundaries(baseStart, exactDesiredX)
    ...
}
deleteSwipeCharOffset = 0                        // 纵向换行后，列偏移重新以行首为基准
```

**这是"上下移动时光标列漂移"的标准解法**：记住一个绝对的 `x`（像素），而不是记住"第几个字符"。横移之后必须让 `exactHorizontalMoved = true`，下一纵移重新采样 `x` —— 否则你先左移再上移，会朝着旧列"斜着走"。

另外两个细节：

- **短行 clamp**：`columnOffset()` 找不到精确 x 就取最近字符，天然落在行尾，不会越界。
- **代理对/组合字符**：`actualSteps()` :897-914 用 `loopOverCodePoints` 校正步数，避免把 emoji 切成半个。

## 6. 他们踩过的坑（按重要性排序）

1. **拿 `\n` 当视觉行** —— 软换行完全失效。IME 侧拿不到 `Layout`，只能靠 B 路径或委托。
2. **`META_SHIFT_ON` 单独用不管用** —— 必须补 `SHIFT_LEFT` down/up 事件（:203-217）。
3. **`requestTextBoundsInfo` 返回区间不覆盖锚点** —— 必须校验 `startIndex/endIndex`，并重试一次全文本（:717）。
4. **回调是异步的** —— 不缓存 pending 步数，用户快速上滑会被吞掉几个 step。
5. **不判 `isMultiLine`** —— 单行框里请求逐字符矩形纯属浪费，且行几何无意义（:674）。
6. **不缓存"不支持"的包名** —— 每个手势都等 150 ms 超时，体验明显发涩。
7. **行首判定不看前一个字符** —— 首行不完整导致整体错一行（:771）。
8. **`setSelection` 之后立刻 `getTextBeforeCursor` 读光标** —— `setSelection` 是异步 IPC；他们全程用自己维护的 `expectedSelectionStart/End`（`RichInputConnection.kt:1557`）和 `tryFixIncorrectCursorPosition()`（:1517）纠偏。
9. **长文本绝对偏移换算** —— 快照只有 2000 字符，务必用 `textStartOffset = end - text.length` 换算回绝对偏移（:773）。
10. **触觉反馈节流** —— 每 2 步一次（`stepCount % 2`），否则连续滑行震得像马达坏了。

## 7. 排查清单：你的"换视觉行"卡在哪

| 症状 | 最可能原因 | 先查这里 |
|---|---|---|
| 上/下移一行，光标跳到行首或文首 | `DPAD_UP` 没被编辑器消费；或误用了 `MOVE_HOME` | 是否 `sendKeyEvent` 而非 `commitText`；编辑器是否 WebView |
| 跨软换行时位置对，跨硬换行错（或反之） | 混用逻辑行/视觉行 | 你的行首判定是 `\n` 还是几何 |
| 上下移动时列慢慢漂移 | 没有固定 `x`，或横移后没重采样 | `exactDesiredX` 的生命周期 |
| 选区方向反了 / 一动就塌陷 | `setSelection(a,b)` 参数顺序；锚点用了 start 而非 end | `coerceIn` + 固定锚点 |
| 少选/多选一行 | TextBoundsInfo 首行不完整未 `drop(1)` | `firstIsRealLineStart` |
| 只在部分 App 失效 | 编辑器不支持 `requestTextBoundsInfo` | 加包名黑名单 + 降级 |
| 快速连续滑动错乱 | 异步结果串了 | `generation` / `pendingSteps` |
| emoji、泰文、组合音标处错位 | 按 UTF-16 code unit 计数 | `actualSteps()` 的码点校正 |
| 长文（>2000 字符）偏移全错 | 快照截断未换算 | `textStartOffset` |

## 8. 最小实现骨架

```kotlin
// 1) 会话开始就要 cursor updates，否则没有锚点
override fun onStartInput(...) { connection.requestCursorUpdates(true, true) }

// 2) 纯移动：直接交给编辑器，别自己算
fun moveLine(dir: Int, extend: Boolean) {
    val code = if (dir < 0) KEYCODE_DPAD_UP else KEYCODE_DPAD_DOWN
    if (extend) sendKey(ACTION_DOWN, KEYCODE_SHIFT_LEFT, 0)
    sendKey(ACTION_DOWN, code, if (extend) META_SHIFT_ON else 0)
    sendKey(ACTION_UP,   code, if (extend) META_SHIFT_ON else 0)
    if (extend) sendKey(ACTION_UP, KEYCODE_SHIFT_LEFT, 0)
}

// 3) 需要固定锚点跨行扩选：请求几何
fun onVerticalStep(dy: Int) {
    val g = geometry ?: run { requestGeometry(); pendingY += dy; return }
    val x = desiredX.takeIf { !it.isNaN() } ?: g.xAt(anchor).also { desiredX = it }
    lineIndex = (lineIndex - dy).coerceIn(0, boundaries.lastIndex)
    val start = boundaries[lineIndex].let { g.columnOffset(it, x) }
    connection.setSelection(min(start, anchor), max(start, anchor))
}
```
