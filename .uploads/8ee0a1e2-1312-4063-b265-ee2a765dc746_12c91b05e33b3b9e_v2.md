## 二、理解一切的前提：`InputConnection` 的坐标系

这是所有缺陷的共同背景。四个 API 各自以不同位置为基准：

| 调用 | 返回区间 | 基准点 |
|---|---|---|
| `getTextBeforeCursor(n, 0)` | `[max(0, min - n), min)` | 选区**左端** `min(start,end)` |
| `getTextAfterCursor(n, 0)` | `[max, min(N, max + n))` | 选区**右端** `max(start,end)` |
| `getSelectedText(0)` | `[min, max)` | 选区本身 |
| `setSelection(a, b)` | 之后 `start=a, end=b`（**允许 a > b**） | — |

🟡 前两行是**推断**，依据是两次实测的对称现象：

1. 光标在句尾，连按「←」能逐次扩展（若以右端为基准，`before.length` 会恒为 6，第一次之后不动）→ 说明以左端为基准。
2. 同一位置向右收缩失效，而中间位置正常（见 D-02 推演）→ 说明 `after` 以右端为基准。

两点同时成立，才能解释「向左正常、向右卡死」。若只读 `getTextBeforeCursor` 的单侧行为，会得出矛盾结论，所以这里的推断置信度标为高，而非已核实。

**关键推论**：`before.length + after.length = N - 选区宽度`。
只要存在选区，这两个 API 拼起来就是**残缺的全文**，中间那一段被跳过了。D-02、D-03 的 End 分支、D-04 的 down 分支都栽在这一点上。

## 三、缺陷详述

### D-01 向右扩展只能动一次

**代码**（第 203–214 行）

```kotlin
private fun extendSelection(ic: InputConnection, direction: Int) {
    val before = ic.getTextBeforeCursor(SAFE_TEXT_LIMIT, 0) ?: ""
    val after  = ic.getTextAfterCursor(SAFE_TEXT_LIMIT, 0) ?: ""
    val pos = before.length
    val total = before.length + after.length
    val next = (pos + direction).coerceIn(0, total)
    if (next != pos) {
        ic.beginBatchEdit()
        ic.setSelection(editSelAnchor, next)
        ic.endBatchEdit()
    }
}
```

**推演**（文本「今天天气不错」，N = 6；光标在位置 0，`select_begin` 记 `anchor = 0`）

| 步骤 | `before.length` | `next` | 写入 | 选区 | 观察 |
|---|---|---|---|---|---|
| → 第 1 次 | 0 | 1 | `(0,1)` | `[0,1]` | 选中第 1 字 ✅ |
| → 第 2 次 | 0 | 1 | `(0,1)` | `[0,1]` | 无变化 ❌ |
| → 第 3 次 | 0 | 1 | `(0,1)` | `[0,1]` | 无变化 ❌ |

**根因 R-1**：`anchor` 固定为 0，`setSelection(0, next)` 让选区左端恒为 0，
`before.length` 因此恒为 0，`next` 恒为 1 —— **读回的输入就是自己刚写进去的**。

**向左为什么正常**：选区 `[p-1, p]`，左端是 `p-1`，恰好等于活动端，
`pos` 随活动端移动，`next = p-2` 每次都是新值。

**影响**：选择模式实质不可用，用户只能逐次重进模式再选一个字。

---

### D-02 句尾向右收缩无响应

**同一段代码**，问题出在 `total`。

**推演**（同一文本，N = 6；光标在句尾 6；`anchor = 6`）

| 步骤 | 选区 | `before.length` | `after.length` | `total` | `next` | 结果 |
|---|---|---|---|---|---|---|
| ← ×1 | `[5,6]` | 5 | 0 | 5 | 4 | 扩展 ✅ |
| ← ×2 | `[4,6]` | 4 | 0 | 4 | 3 | 扩展 ✅ |
| ← ×3 | `[3,6]` | 3 | 0 | 3 | 2 | 扩展 ✅（「气不错」） |
| → ×1 | `[3,6]` | 3 | 0 | **3** | `(3+1).coerceIn(0,3)=3` | **无变化** ❌ |

**根因 R-2**：

```
total = min + (N - max) = N - 选区宽度
```

句尾时 `after` 为空，`total` 退化成 **选区左端位置**（3），
而想往右扩需要 `next = 4 > total`，被 `coerceIn` 钳回 3，
写入的区间与当前完全一致 → 画面不动。

**为什么中间正常**：`after` 非空，`total` 大于选区右端，`next` 不会被钳。

**注意**：这不是「选区被清空」。若按方向继续走到 `next == pos`，`if (next != pos)` 会直接跳过，
连 `setSelection` 都不执行。现象是「按了没反应」，不是「选区消失」。

**影响**：句尾是最高频的选择场景（选最后一句、选末尾几个字），基本不可用。

---

### D-03 Home / End 使用绝对坐标

**代码**（第 141–146 行）

```kotlin
"home" -> ic.setSelection(0, 0)
"end" -> {
    val before = ic.getTextBeforeCursor(SAFE_TEXT_LIMIT, 0) ?: ""
    val after = ic.getTextAfterCursor(SAFE_TEXT_LIMIT, 0) ?: ""
    ic.setSelection(before.length + after.length, before.length + after.length)
}
```

**两个问题叠加**：

1. `0` 是**文档起点**，不是行首。
2. `End` 的 `before + after` 在**存在选区时**同样漏算宽度（R-2），
   会停在 `N - 宽度` 的位置，比真正的末尾靠前。

**影响**：长文本按一次 Home 位移数百行；同时触发 L-01 丢弃拼音编码——
用户感知为「输入法把刚打的字吃了」。

---

### D-04a 上下选择跳到行首/行尾（多行文本）

**代码**（第 176–199 行）

```kotlin
"select_arrow_up" -> {
    val pos = before.length
    val prevNewline = before.lastIndexOf('\n', pos - 2)
    val lineStart = if (prevNewline >= 0) prevNewline + 1 else 0
    ic.setSelection(editSelAnchor, lineStart)      // 目标：某个行首
}
"select_arrow_down" -> {
    val lineEnd = if (nextNewline >= 0) pos + nextNewline else total
    ic.setSelection(editSelAnchor, lineEnd)        // 目标：某个行尾
}
```

**推演**（`aaa\nbbb\nccc`，索引 a0 a1 a2 ␊3 b4 b5 b6 ␊7 c8 c9 c10；活动端在第二行第 3 列，即位置 7）

| 步骤 | 计算 | 目标位置 | 实际效果 |
|---|---|---|---|
| ↑ | `prevNewline = lastIndexOf('\n', 5) = 3` → `lineStart = 4` | 4（第二行行首） | 选区伸到**本行行首**，列丢失 |
| ↑↑ | 若已在行首，`pos-2` 落在上一行内 → 上一行行首 | 4 → 0 | 才真正跨行 |

**根因 R-4**：目标是「行首/行尾」而不是「上一行同列位置」，没有计算列号。

**副作用**：向上本应移动一格，实际一次移动「当前列号」个字符，跨度不可预测。

### D-04b 单段落长文本按「↑」选中上方全部（重点）

**这是你最新发现的现象，与 D-04a 同源但后果严重得多。**

**代码路径**：`lastIndexOf('\n', pos - 2)` 在无换行的文本里返回 `-1`，
三元表达式走 `else 0` 分支：

```kotlin
val lineStart = if (prevNewline >= 0) prevNewline + 1 else 0   // ← 兜底 0
ic.setSelection(editSelAnchor, lineStart)                       // → (anchor, 0)
```

`setSelection(anchor, 0)` 允许反向，于是把选区从文档开头一直拉到光标处。

**推演**（一整段无 `\n` 的文本，N = 2000，光标在位置 800）

| 量 | 值 |
|---|---|
| `pos = before.length` | 800 |
| `lastIndexOf('\n', 798)` | `-1`（无换行） |
| `lineStart` | **0** |
| `setSelection(800, 0)` | 选区 `[0, 800]` |

结果：**一次按键选中上方 800 个字符**。向下对称，`lineEnd = total`，选到文末。

**三个独立因素共同导致**：

| 因素 | 作用 |
|---|---|
| 只认 `\n`，不认自动换行 | 整段被当成一行，逻辑上「没有上一行」 |
| 兜底值取 `0` 而不是「不动」 | 把「无上一行」翻译成「跳到文档开头」 |
| `setSelection` 接受反向区间 | 悄无声息地形成大选区，不报错 |

**这不是 D-01/D-02 的问题**：没有 ±1 扩展，也没有 `coerceIn` 钳位，是纯粹的边界兜底选择。

**是否 bug**：取决于参照物。
- 对桌面编辑器（按逻辑行）：首行按 ↑ → 文档开头，是**标准行为**。
- 对移动端用户（按视觉行）：一整段自动折行成 20 屏，按 ↑ 只该动一行，**这就是 bug**。

### L-01 移动光标丢弃拼音组合态

`onUpdateSelection`（XimeInputMethodService.kt:2485）判定新旧选区不等 →
`breakPendingCompositionForCaretMove()` → `rimeEngine.clearComposition()`。

日志：

```
onUpdateSelection: 丢弃待上屏组合态 (a,b)->(c,d)
```

**性质**：主动设计，避免编码与光标错位，不是缺陷。
但 D-03 让误触概率大增（Home 一跳几百行），所以体感上是「缺陷的放大器」。

### U-01 `getSelectedText()` 的可用性（未验证）

修复补丁依赖 `ic.getSelectedText(0)` 补齐全文。风险：

| 宿主类型 | 常见表现 |
|---|---|
| `EditText` / `AppCompatEditText` | 正常返回 |
| WebView 输入框 | 可能返回 null 或空串 |
| Flutter / Compose 自绘输入框 | 取决于实现 |

若返回 null，`snapshotText()` 会退化成 `before + after`，**D-02 复现**。
兜底方案见第八章「决策点 B」。

## 六、D-04b 的处理选项

| 方案 | 行为 | 优点 | 代价 |
|---|---|---|---|
| **A. 首行不动**（推荐） | `lineStart == 0` 时 `extent` 保持不变 | 不会误选大段；「全选」按钮仍在 | 想扩到开头需连按「←」 |
| **B. 保持到 0** | 现状 | 符合逻辑行语义，和桌面编辑器一致 | 长段落里一次选中上千字 |
| **C. 视觉行** | 按屏幕折行移动 | 最符合移动端直觉 | **输入法侧做不到**，需要宿主 `Layout`，`InputConnection` 不暴露 |

A 的改法（两行）：

```kotlin
val target = if (direction < 0) {
    if (lineStart == 0) {
        editSelExtent          // 已在首行，原地不动
    } else { /* 上一行同列 */ }
} else {
    if (lineEnd >= total) {
        editSelExtent          // 已在末行，原地不动
    } else { /* 下一行同列 */ }
}
```

注：C 并非完全无解——若宿主是 `EditText`，可通过 `InputMethodService` 拿到
`EditorInfo` 但拿不到 `Layout`；真要按视觉行，只能由宿主 App 提供信息，输入法无能为力。
Xime 作为通用输入法，应当按逻辑行设计并在文档中说明。

## 八、继续取证的探针

若要我进一步确认 R-1 / R-2 / U-01，最直接的方法是在补丁里加一行日志，
编译后跑一次固定用例，把日志贴回来即可定位到具体 API 行为。

在 `extendSelection` 开头插入：

```kotlin
android.util.Log.d(
    "XimeSel",
    "dir=$direction anchor=$editSelAnchor extent=$editSelExtent " +
    "before=${ic.getTextBeforeCursor(100000, 0)?.length} " +
    "after=${ic.getTextAfterCursor(100000, 0)?.length} " +
    "selected=${ic.getSelectedText(0)?.length}"
)
```

然后：

```bash
adb logcat -s XimeSel
```

依次做「句尾 ←×3 →×1」，观察 `selected` 是否为 `3`：

| 日志特征 | 结论 |
|---|---|
| `selected=3` | U-01 无风险，`snapshotText()` 可用 |
| `selected=null` 或 `0` | 需要改用 `|anchor-extent|` 兜底（决策点 B） |
| `before + after + selected ≠ N` | 该宿主对某 API 有额外截断，需按宿主做适配 |

**决策点 B（若 U-01 成立）**：用我们自维护的端点距离代替 `getSelectedText()`：

```kotlin
val width = kotlin.math.abs(editSelAnchor - editSelExtent)
val total = before.length + width + after.length
```

因为选区两端本来就是 `anchor` / `extent`，宽度无需询问宿主。
代价：外部改过选区时该值失真，需在 `onUpdateSelection` 里清空状态。
