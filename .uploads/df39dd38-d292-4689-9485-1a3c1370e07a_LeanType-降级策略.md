# LeanType「视觉行」能力的降级策略

> 单独抽出的专题文档。完整功能分析见同目录 `LeanType-视觉行实现分析.md`（第 4.5 节与本文件内容一致）。
> 代码位置对应 `LeanBitLab/LeanType` `main` 分支快照。

---

## 一句话概括

LeanType 的降级不是"出错才补救"，而是 **估算先行、精确后补**：滑动一开始就有一份粗糙但立即可用的行边界，精确几何异步到达后，在**语义等价点**上原地替换。

这个顺序是整套设计的地基。反过来做（先等精确数据、失败再估算），就会在"等"和"跳"之间二选一。

---

## 1. 三层能力与降级方向

| 层 | 手段 | 何时用 | 失败后 |
|---|---|---|---|
| A | `sendKeyEvent(DPAD_*)`，扩选时补 `SHIFT_LEFT` down/up | 只需移动/扩选，编辑器可控 | **无降级**（见第 5 节，这是缺口） |
| B | `requestTextBoundsInfo()` + `CursorAnchorInfo` 自建几何 | 需固定锚点任意跨行扩选 | 降到 C |
| C | `\n` 分段 + 每 40 字符在空白处断行 | B 不可用、超时、被拉黑 | 无更下层，只能接受误差 |

## 2. 九道闸门

前六道在**发请求之前**判定，任何一道不过就直接用 C，且不发任何 IPC：

| # | 闸门 | 位置 | 不通过时 |
|---|---|---|---|
| 1 | `SDK_INT >= 34` | :672 | 静默走 C |
| 2 | `keyboardId.isMultiLine` | :674 | 静默走 C（单行框算行无意义） |
| 3 | 包名不在黑名单 | :675 | 静默走 C |
| 4 | `lastCursorAnchorInfo != null` | :678 | 静默走 C（拿不到行高就构不出查询矩形） |
| 5 | `lineHeight > 0 && !NaN` | :681 | 静默走 C（编辑器上报了坏值） |
| 6 | 请求发送成功 | :691 | 走 C |

后三道在**结果回调里**判定：

| # | 校验 | 失败动作 |
|---|---|---|
| 7 | `info != null` | 超时/失败 → 拉黑包名 + C |
| 8 | `info` 区间覆盖 `baseStart` | **重试一次**全文本矩形，仍失败才拉黑 |
| 9 | `boundaries.size > 1` | 只拿到一行 → 无法上移 → 拉黑 |

> 1~6 全是**能力探测**，不是 try/catch。用异常做流控会让降级路径不可预测；而且 `requestTextBoundsInfo` 跨进程失败时未必抛异常（走 `null` 回调），必须显式判返回值和回调内容。

## 3. 时序

```
手势开始
  ├─ getTextBeforeCursor(2000)                    ← 文本快照
  ├─ getLineBoundariesBackwards()                 ← C 立即可用（表已就绪）
  └─ getWordBoundariesBackwards()                 ← 词模式同理
        │
第一次纵向位移
  ├─ requestExactLines()                          ← 一次性，每手势只问一次
  │    └─ 构造 RectF = 全宽 × [markerTop-40行, markerBottom]
  ├─ pendingStepsY += stepsY; stepsY = 0          ← 冻结
  └─ postDelayed(150ms) 超时兜底
        │
   ┌────┴─────────────────────────┐
   │ 回调成功                      │ 回调 null / 超时
   ├─ 校验区间覆盖 baseStart       ├─ 拉黑包名
   ├─ 重建 VisualLines 几何        ├─ 保留 C 表
   ├─ 零副作用检查通过 → 换表       │
   └─ 重放 pendingStepsY           └─ 重放 pendingStepsY
```

## 4. 三个关键设计

### 4.1 切换点必须"零副作用"

滑动开始时 C 表已经建好（`onMoveDeletePointer` :585-605）：

```kotlin
deleteSwipeInitialText    = getTextBeforeCursor(2000)
deleteSwipeLineBoundaries = getLineBoundariesBackwards(textBefore, baseStart)   // C
```

B 到达后原地替换，但有个前置条件（`onExactLinesResult` :731-739）：

```kotlin
if (deleteSwipeLineIndex == 0 && deleteSwipeLineBoundaries.firstOrNull() == baseStart) {
    exactGeometry = geometryFromTextBoundsInfo(info, baseStart)
}
```

条件含义：**用户还没产生任何纵向位移（`lineIndex == 0`）、锚点也没变**。此时两张表的索引 0 都是 `baseStart`，替换后选区一个像素都不动。

若在 C 上已走了 3 行再换表，索引语义立刻错位，只能重置手势——用户会看到选区跳回去。所以他们宁可让 B 等一等。

**可搬原则**：精度升级只能发生在语义等价的点上，否则宁可不升级。

### 4.2 冻结，而不是预测

| 策略 | 行为 | 代价 |
|---|---|---|
| 预测 | 先按 C 走，B 回来再纠正 | 选区闪跳两次，用户明确可见 |
| **冻结**（采用） | `stepsY` 扣住，累加到 `pendingStepsY`，回调后重放 | 首次上滑最多 150 ms 延迟 |

```kotlin
// :600-606
if (deleteSwipeExactPending && stepsY != 0) {
    deleteSwipePendingStepsY += stepsY
    stepsY = 0                    // 本次不产生位移
}
// 回调末尾 :740-742
if (pending != 0) moveDeletePointer(0, pending)
```

能接受冻结，是因为这是**长按拖动**的连续手势：起手 150 ms 感知很弱，步数也不丢（累积重放）。单次点按的编辑键绝不能这么干。

**待改进**：快速连滑十几行时，150 ms 后一次性重放会变成"手停了才动一下"的大跳。加个上限——`pendingSteps > 8` 就放弃精确模式转 C，把滞后压在可感知阈值内。

### 4.3 降级的记忆粒度

| 粒度 | 变量 | 生命周期 | 作用 |
|---|---|---|---|
| 每手势 | `deleteSwipeExactRequested` | 一次滑动 | 只问一次，不是每步都问 |
| 每应用 | `noTextBoundsPackage` | 键盘进程 | 一次失败，后续不再问 |

两个已知缺陷：

- 是**单值 `String` 而不是 `Set`**（:579）。在两个都不兼容的 App 之间来回切，每次都要重新等 150 ms。
- 只被赋值、**从不清空**（全文件仅 :726 / :735 两处写）。跨会话复用是优点，但那个 App 修好了也仍被拉黑，直到进程被杀。加版本号或时间戳更稳。

## 5. 缺口：A 路径没有降级

`RichInputConnection.sendKeyEvent()` :907 返回 `Unit`，**丢弃了 `InputConnection.sendKeyEvent()` 的 Boolean**：

```kotlin
fun sendKeyEvent(keyEvent: KeyEvent) {   // 无返回值
    ...
    if (isConnected()) mIC?.sendKeyEvent(keyEvent)   // 结果被忽略
}
```

编辑器吃掉 `DPAD_UP` 时，LeanType 完全不知道——方向键、空格上下滑、触摸板移动全部静默失效，无兜底、无提示。

**补法很便宜**：`onUpdateSelection` 本来就是编辑器回传的选区变化（`InputLogic.kt:189`），直接当回执：

```
发完一组 DPAD，记下 (selStart, selEnd)
200 ms 内 onUpdateSelection 没报到变化 → miss++
连续 3 次 miss → 标记该包 "DPAD 不支持"，改用 B/C 自行 setSelection
```

比等用户反馈"上下键没反应"早得多。

## 6. 五条可搬的原则

1. **同构数据**：C 与 B 产出同一种结构（`List<Int>` 行锚点表），替换零成本。异构输出会逼你写两套状态机。
2. **估算先行**：默认路径永远可用，不依赖任何可选能力。B 只是加分项，不是必经之路。
3. **探测而非捕获**：能提前判的能力全部前置，别让异常当分支。
4. **升级要无副作用**：只在语义等价点替换数据，否则宁可不升级。
5. **降级要留痕**：至少统计降级率（每包 / 每版本）。没有埋点，你永远不知道功能在多少 App 里其实是坏的。

---

## 7. 中文场景的额外提醒

C 路径靠空白字符断行，**中文、日文没有词间空格**，`breakPoint` 会一路退到 `lineStart`，退化成"整段一行"。加上等宽全角、行首禁则（标点不出现在行首），字符数估算会系统性偏 1~2 字。

两条路可选：

- 承认 C 不可用，降级成"按逻辑行/段落扩选"——语义正确、粒度粗，用户能理解；
- 干脆去掉二维行选，只保留 A 路径的方向键移动。

**不要用字符数估算去假装视觉行。** "偶尔差一个字"比"没有这个功能"更让人抓狂。
